# Fuzzing and sanitizers

ROB-09 says: *no frame parser crashes, 24 h of random-data testing*. Until now
that was approached by 200 000 home-made random buffers inside the unit tests
(`core/tests/test_frame_fuzz.c`). This is the real thing: three fuzz targets,
real sanitizers, a real corpus, a bounded budget for CI and a 24 h mode.

Everything lives in `host/fuzz/`. Nothing here touches `core/`.

## Targets

| target | what it drives | requirements |
|---|---|---|
| `fuzz_frame.c` | `relais_frame_decode` and `relais_frame_decode_unchecked`, at level S (CRC-32C) and level C (keyed SipHash MAC) | ROB-09, SEC-01, SEC-02, ROB-02 |
| `fuzz_journal.c` | the three classifiers, the three parsers and the three formatters of the journal, plus a format→parse round trip | OBS-01, OBS-02, DET-04, ROB-09 |
| `fuzz_arbiter.c` | `relais_arb_step` driven by a **script** of event choices, and `relais_arb_snapshot`/`restore` | MAN-02, MAN-04, MAN-10, MAN-11, DET-03, ACT-05, SEC-04 |

The arbiter target is not a parser fuzz: the input bytes are read as a sequence
of steps (`host/fuzz/fuzz_script.h` documents the layout), each step building the
messages fed to the arbiter at the next tick. Half of the messages are *aligned*
with the arbiter's current state — sender, mandate and tick taken from it — so
the orders are really accepted and the deep branches are reached: handover,
auto-switch to a certified second, certification, disagreement, testament,
fallback, demande rate limiting. Fuzzing only the parser would never get there.

Each target also checks contracts, not just memory safety. A violated contract
traps (`fuzz_require` in `host/fuzz/fuzz_util.h`), which stops the run, prints
the file and line, and keeps the input. Examples: an accepted frame must carry
the control its key computes (SEC-02); decoding twice must give the same bytes
(ROB-02); exactly one value is applied per tick and it is inside the ACT-05
bound; the mandate never goes backwards; a formatted journal line must always
parse back with the same values.

## Backends

The same `LLVMFuzzerTestOneInput` entry points are built two ways, chosen
automatically by `host/fuzz/Makefile` with a probe compile:

1. **clang + libFuzzer** (preferred): `-fsanitize=fuzzer,address,undefined`,
   coverage guided, `-dict=host/fuzz/frame.dict`, artifacts written straight into
   `host/fuzz/corpus/crashes/`.
2. **gcc + ASAN/UBSAN** (fallback, and what ran on this machine): clang is not
   installed here, so the targets are linked with `host/fuzz/fuzz_driver.c`, a
   home-grown driver: a seeded xorshift64\* generator producing random buffers
   plus havoc mutations of the corpus (bit flip, byte set, interesting values,
   insert, delete, splice, chunk overwrite), `-fsanitize=address,undefined
   -fno-sanitize-recover=undefined`, and a chained signal handler that writes the
   failing input to the crash file. The Makefile and every run print
   `FUZZ-BACKEND homegrown (no clang/libFuzzer here)` so the fallback can never
   be mistaken for coverage-guided fuzzing.

The fallback is **not** coverage guided. It compensates partly by starting from
real seeds and mutating them, but a coverage-guided run explores deeper per
second. Installing clang (`apt install clang`, nothing else) switches the same
`make fuzz` command to libFuzzer with no source change.

## Corpus and dictionary

`host/fuzz/corpus/` holds 22 seeds, regenerated by `make corpus`
(`host/fuzz/gen_corpus.c`):

- `frame/` — 10 seeds: one per message type, encoded by the shared
  `relais_frame_encode`, i.e. the exact bytes the simulator, the PC actuator and
  the QNX `relais-net` put on the wire; the STATUT and the ORDRE exist in both
  the CRC and the MAC variant, plus one carrying the bench `TEST` flag.
- `journal/` — 10 seeds: three formatted by the shared formatters, and **seven
  lines copied out of a journal a real simulator run wrote**
  (`relais-simulate --ticks 400 --seed 1007 --journal …`), so the parser is
  seeded with production output rather than with a reconstruction of it.
- `arbiter/` — 2 scripts: `arbiter_nominal_life.bin` (a demande granted, eight
  ticks of holder order + second shadow, then silence and revocation) and
  `arbiter_hostile_flood.bin` (unaligned messages, stale and future mandates,
  demande floods for SEC-06, cessions from a node that is not the holder).

`host/fuzz/frame.dict` gives libFuzzer the tokens of the format: the magic
`RLS1`, the version, the seven type bytes, the five sender bytes, the four flag
bits, the six fixed payload lengths as big-endian u16, five whole plausible
headers, the journal's JSON keys and the arbiter snapshot magic `RARB`.

Every seed was checked before use: each of the three targets was run once on
each of the 22 seeds (66 runs, `--input`), all clean. No seed crashes.

## Results on this machine

`make fuzz` (60 s per target, the CI budget), gcc 13.3.0, Ubuntu 24.04,
12 cores, backend `homegrown`, seed `20261111`. Two runs are reported because
the throughput depends on what else the machine is doing, and quoting only the
best one would be dishonest:

| target | run 1 execs | run 1 exec/s | run 2 execs | run 2 exec/s | crashes |
|---|---:|---:|---:|---:|---:|
| `fuzz_frame` | 24 172 327 | 402 826 | 80 662 190 | 1 344 370 | 0 |
| `fuzz_journal` | 760 897 | 12 682 | 2 592 964 | 43 216 | 0 |
| `fuzz_arbiter` | 4 531 668 | 75 528 | 14 363 440 | 239 391 | 0 |
| **total / 180 s** | **29 464 892** | | **97 618 594** | | **0** |

Run 1 was measured while the machine was busy with other work, run 2 on a quiet
one; the same binaries, the same corpus and the same seed were used for both.
`docs/RESULTS.md` carries run 2 (it is regenerated by `make fuzz-report`).

Reproduce with `make fuzz`; the raw logs are `host/fuzz/logs/*.log`, and
`make fuzz-report` (or `python3 tools/fuzz-report.py --results docs/RESULTS.md`)
rewrites the table into `docs/RESULTS.md` between its `FUZZ-REPORT` markers.

No crash was found. One contract violation *was* found on the first arbiter run
and root-caused to the harness, not to the core: the target asserted
`out->certified_node == a->certified_node`, while `arbiter.c` deliberately
publishes in `out->certified_node` the certification that served this tick's
choice and in `out->statut.certified_node` the state after `certify()`. The
assertion was corrected to compare the STATUT fields; the core was not touched.
This is recorded here because a fuzzer that never fires is worth less than one
whose fires are explained.

## Replaying the 24 h of ROB-09

```sh
make fuzz-long                      # 86 400 s per target, three targets in parallel
make fuzz-long FUZZ_LONG=3600       # one hour per target
make fuzz-long JOBS=4               # libFuzzer only: four workers per target
```

`fuzz-long` runs the three targets concurrently, writes
`host/fuzz/logs/<target>-long.log`, keeps every failing input under
`host/fuzz/corpus/crashes/`, and exits non-zero if any target died. At the rates
measured above, a 24 h run of the fallback backend is worth between
**4.2 × 10¹⁰ and 1.4 × 10¹¹ executions** depending on the load of the machine
(the two bounds are the two runs of the table above). libFuzzer would trade raw
count for depth. It is out of CI on purpose — the CI budget is 5 minutes per
job, and `make fuzz` spends about 3.5 of them.

A kept case is replayed and minimised without any external tool:

```sh
./build/fuzz/fuzz_frame --input host/fuzz/corpus/crashes/crash-….bin --max-len 4096
python3 tools/fuzz-report.py            # delta-debugging minimiser, writes crashes/min/
```

The minimiser is the target binary itself driven by `tools/fuzz-report.py`
(delta debugging: drop chunks, then bytes, while the failure reproduces). On a
704-byte synthetic case it converged to the 4 bytes that matter.
`llvm-symbolizer` is not installed here; gcc's libasan symbolises through
`addr2line`, which is present, so stacks are readable.

## What the fuzzing does NOT cover

- **Protocol semantics.** That a handover is never wrongful, that the two
  computers never command at once, that the lamp follows the cause — that is
  I1…I11, and it is proven by the exhaustive explorer (`make explore`,
  10 000 330 states with two faults, 0 violation) and by the seeded simulator
  campaign (`make campaign`, 19 659 runs, 0 failure), not by a fuzzer. A fuzzer
  finds inputs that break *memory and arithmetic*; it does not know what a
  correct mandate transfer looks like.
- **Timing.** The arbiter is tick driven and has no clock; latency, jitter,
  WCET and the `2*delta + C + J <= T` hypothesis are out of scope here.
- **The transport.** UDP loss, reordering and duplication are the simulator's
  fault model (`--loss`, `--delay`) and the bench's, not the fuzzer's.
- **Concurrency.** The targets are single threaded; the QNX priorities and the
  message passing of `target/` are not exercised.
- **The QNX kernel boundary.** `/dev/relais` and the typed security policy can
  only be opposed on a real target: see `docs/SECURITY-POLICY-DEMO.md`.
- **Anything after the decode.** The control law, the plant model and the
  node state machine are reached only through the arbiter target's messages,
  never through hostile bytes on the wire, because the wire stops at the decoder.
